Functions: Named Arguments

🕒 Created: 2023-10-11 | Updated: 2026-11-24

  • There's no named arguments for functions in any versions.

  • C++20 introduces some workarounds, but they are not great when comparing to what it should be, as done in any decent languages.

  • Some of the solutions here work for C as well.

~Original problem

  • Problems :

    • No named arguments. You have no idea what is happening here.

    • No type distinctions, as it's easy to swap 2 parameters with the same type by mistake. 

// .h
void SomeFunc(
    Object& obj,
    RandomDataArray& randomData,
    const Camera& someCamera,
    ConfigureData configData,
    float dynamicIntensity,
    SomeInfoXL someInfo,
    Shader shader,
    Texture* pTexInput,
    Texture* pTexDepthInput,
    SubTexture* pSubTexA,
    SubTexture* pSubTexB,
    Texture* pTextureOutput);

// .cpp
SomeFunc(
    obj,
    randomData,
    someCamera,
    data,
    dynamicIntensity,
    someInfo,
    *pSomeShader,
    pSomeTexInput,
    pTexDepth,
    pSomeSubTexA,
    pSomeSubTexB,
    pSomeSurface);

~Using comments

  • Problems :

    • No strict types. You can invert the arguments with the same type, and that's an error you can only catch by eye.

    • Comments get outdated extremely easy.

    • This also leaves a huge space and bad indentation in the code. It's very ugly to look at. 

SomeFunc(
    /* obj               = */  obj,
    /* randomData        = */  randomData,
    /* someCamera        = */  someCamera,
    /* configData        = */  data,
    /* dynamicIntensity  = */  dynamicIntensity,
    /* someInfo          = */  someInfo,
    /* shader            = */  *pSomeShader,
    /* pTexInput         = */  pSomeTexInput,
    /* pTexDepthInput    = */  pTexDepth,
    /* pSubTexA          = */  pSomeSubTexA,
    /* pSubTexB          = */  pSomeSubTexB,
    /* pTextureOutput    = */  pSomeSurface);

~Replacing function arguments for a struct

  • Named parameters.

  • Type safe.

  • Problems :

    • No parameters inside the struct are required.

    • If you forget to initialize a parameter, you can at max get a runtime assert.

    • You require a separate data struct just to use this, which makes the declaration and function internals more confusing that it needed to be.

    • The cost to get named arguments can be too much. 

// .h
struct SomeFuncResources {
    float dynamicIntensity  = 0.0f;
    SomeInfoXL someInfo     {};
    Texture* pTexInput      = nullptr;
    Texture* pTexDepthInput = nullptr;
    SubTexture* pSubTexA    = nullptr;
    SubTexture* pSubTexB    = nullptr;
    Texture* pTextureOutput = nullptr;
};
void SomeFunc(
    Object& obj,
    RandomDataArray& randomData,
    const Camera& someCamera,
    ConfigureData configData,
    SomeFuncResources res,
    Shader& shader); 

// .cpp
SomeFuncResources res{};
res.someInfo            = someInfo;
// res.dynamicIntensity = dynamicIntensity;  // <- forgetting something doesn't cause a crash.
res.pTexInput           = pSomeTexInput;
res.pTexDepthInput      = pTexDepth;
res.pSubTexA            = pSomeSubTexA;
res.pSubTexB            = pSomeSubTexB;
res.pTextureOutput      = pSomeSurface;
SomeFunc(
    obj,
    randomData,
    someCamera,
    data,
    res,
    *pSomeShader);

~Trying to enforce complete initialization via RequiredInit  template

  • Using a wrapper around any value or pointer T that tracks initialization.

  • Forgetting something will cause a RUNTIME CRASH while inside the SomeFunc  function, as soon as the argument is read from.

  • #ifdef ASSERTS_ENABLED

    • ASSERT  triggers at runtime if the value is read before being assigned.

    • Adds a 1-byte mIsSet  flag (plus alignment padding, typically doubling the field's stack footprint).

  • #else

    • No ASSERT  is triggered.

    • The variable mIsSet  is not defined, so no increase in memory footprint.

  • Problems :

    • The assert is extremely late, only called when something reads from the argument not manually initialized.

    • You are still having to deal with structs.

    • You are changing the actual types the function was originally asking for. There's a extra level of indirection via the RequiredInit  template.

    • Minor: There's a memory cost in debug builds. 

// lib
template <typename T>
class RequiredInit
{
public:
    RequiredInit() = default;

    void operator=(T val)
    { 
        mVal = val;
#ifdef ASSERTS_ENABLED 
        mIsSet = true;
#endif
    }
    operator T() const 
    { 
        ASSERT_MSG(mIsSet, "Field was never initialized!"); 
        return mVal;
    }
    T operator->() const
    { 
        ASSERT_MSG(mIsSet, "Field was never initialized!"); 
        return mVal;
    }
private:
    T mVal{};
#ifdef ASSERTS_ENABLED 
    bool mIsSet = false;
#endif
};

struct SomeFuncResources {
    // Config
    RequiredInit<float> dynamicIntensity;
    RequiredInit<SomeInfoXL> someInfo;
    // Input
    RequiredInit<Texture*> pTexInput;
    RequiredInit<Texture*> pTexDepthInput;
    // Scratch
    RequiredInit<SubTexture*> pSubTexA;
    RequiredInit<SubTexture*> pSubTexB;
    // Output
    RequiredInit<Texture*> pTextureOutput;
};

// .cpp
SomeFuncResources res{};
res.someInfo            = someInfo;
// res.dynamicIntensity = dynamicIntensity;  // <- forgetting something will cause a RUNTIME CRASH while inside the `SomeFunc` function, as soon as the argument is read from.
res.pTexInput           = pSomeTexInput;
res.pTexDepthInput      = pTexDepth;
res.pSubTexA            = pSomeSubTexA;
res.pSubTexB            = pSomeSubTexB;
res.pTextureOutput      = pSomeSurface;
SomeFunc(
    obj,
    randomData,
    someCamera,
    data,
    NAMED_ARG(float, dynamicIntensity) = 4.0f,        
    res,
    *pSomeShader);

Wrapping the type with a struct

  • Named parameters.

  • All parameters are required.

  • Type safe.

  • Problems :

    • The NameOfTheArg { theValue }  can be "ok" at the call site, but is very very confusing in the function declaration and internal implementation, as you have no idea what the underlying type actually is. It's not friendly at all.

    • The types have to be declared inside a namespace, otherwise you get conflicts between parameters with the same name between functions.

    • It's very easy to argue that the extra boiler plate does more harm than good. 

// lib
#define PARAM_STRUCT(Name, Type) \
    struct Name \
    { \
        Type value; \
        operator Type() const { return value; } \
        Type operator->() const { return value; } \
        decltype(auto) operator*() const { return *value; } \
    }
    
// .h
namespace SomeFunc_Args
{
    PARAM_STRUCT(pTexInput,      Texture*)
    PARAM_STRUCT(pTexDepthInput, Texture*)
    PARAM_STRUCT(pSubTexA,       SubTexture*)
    PARAM_STRUCT(pSubTexB,       SubTexture*)
    PARAM_STRUCT(pTextureOutput, Texture*)
}
void SomeFunc(
    const Camera& someCamera,
    SomeInfoXL someInfo,
    float dynamicIntensity,
    ConfigureData configData,
    SomeFunc_Args::pTexInput pTexInput,
    SomeFunc_Args::pTexDepthInput pTexDepthInput,
    SomeFunc_Args::pSubTexA pSubTexA,
    SomeFunc_Args::pSubTexB pSubTexB,
    SomeFunc_Args::pTextureOutput pTextureOutput); 

// .cpp
SomeFunc(
    /* obj               = */  obj,
    /* randomData        = */  randomData,
    /* someCamera        = */  someCamera,
    /* configData        = */  data,
    /* dynamicIntensity  = */  dynamicIntensity,
    /* someInfo          = */  someInfo,
    /* shader            = */  *pSomeShader,
    pTexInput       { pSomeTexInput },
    pTexDepthInput  { pTexDepth },
    pSubTexA        { pSomeSubTexA },
    pSubTexB        { pSomeSubTexB },
    pTextureOutput  { pSomeSurface) };

Using NamedType  lib

  • FluentC++ - Strong Types: Named Constructors

  • FluentC++ - Strong Types: Strong Types for Strong Interfaces

  • FluentC++ - Passing strong types by reference

  • FluentC++ - Strong types are free in release builds

  • FluentC++ - Named arguments

  • Problems :

    • Same underlying problems as 'Wrapping the type with a struct': you are changing the underlying type and making things much more confusing.

    • You have to put the new types inside a namespace, so it doesn't create conflicts.

    • Changing the underlying types also makes the internals of the function much more fragile; syntax like myReference.SomeFunction  can be troublesome, as there's no way to overload the dot operator in C++17. 

// lib
// It's approximately this:
template <typename T, typename Parameter>
class NamedType
{
public:
    explicit NamedType(T const& value) : value_(value) {}
    template<typename T_ = T>
    explicit NamedType(T&& value,
        typename std::enable_if<!std::is_reference<T_>{},
        std::nullptr_t>::type = nullptr)
    : value_(std::move(value)) {}

    struct argument
    {
        template<typename UnderlyingType>
        NamedType operator=(UnderlyingType&& value) const
        {
            return NamedType(std::forward<UnderlyingType>(value));
        }
        argument() = default;
        argument(argument const&) = delete;
        argument(argument&&) = delete;
        argument& operator=(argument const&) = delete;
        argument& operator=(argument&&) = delete;
    };
    T& get() { return value_; }
    T const& get() const {return value_; }
private:
    T value_;
};

// .h
namespace SomeFunc_Args
{
    using DynamicIntensity = NamedType<float, struct DynamicIntensity>;
}
void SomeFunc(
    // ...
    SomeFunc_Args::DynamicIntensity dynamicIntensity
    // ...);

// .cpp
SomeFunc(
    // ...
    SomeFunc_Args::DynamicIntensity(4.0f),
    // ...);

  • You can also use the ::argument  part of it to have a better syntax via constructing the underlying type via operator= . 

// .h
namespace SomeFunc_Args
{
    using DynamicIntensity = NamedType<float, struct DynamicIntensity>;
    static const DynamicIntensity::argument dynamicIntensity;
}
void SomeFunc(
    // ...
    SomeFunc_Args::DynamicIntensity dynamicIntensity
    // ...);

// .cpp
SomeFunc(
    // ...
    SomeFunc_Args::dynamicIntensity = 4.0f,
    // ...);

Trying to keep the underlying type visible 

// lib

// ... all the rest

#define NAMED(type, paramName) \
    NamedType<type, struct paramName> paramName
#define NAMED_ARG(type, paramName) \
    (NamedType<type, struct paramName>::NameTypedAssignmentConstructor{})

// .h
void SomeFunc(NAMED(float, dynamicIntensity));

// .cpp, at the call site
SomeFunc(
    NAMED_ARG(float, dynamicIntensity) = 4.0f);

// .cpp
void SomeFunc(NAMED(float, dynamicIntensity))
{
    float fadeIntensity = 1.0f;
    // ...
    fadeIntensity *= dynamicIntensity;
    // ...
}

Using a separate function that accept operator=  constructors

  • Named parameters.

  • All parameters are required.

  • Type safe.

  • The syntax can be weird, but even though you are using a lot, the function implementation is completely untouched.

  • The new function created is overloaded with the existing implementation, so it should be plug-and-play.

  • Check the lib at: [link].

  • Problems :

    • You are duplicating the names for FUNCTION_NAMED_ARGS .

    • The names inside FUNCTION_NAMED_ARGS  can technically be anything.

    • There's error handling in case of number of arguments mismatch, but still, it's the programmer's job to keep these names and order in sync with the function declaration. 

// .h
void SomeFunc(
    Object& obj,
    RandomDataArray& randomData,
    const Camera& someCamera,
    ConfigureData configData,
    float dynamicIntensity,
    SomeInfoXL someInfo,
    Shader shader,
    Texture* pTexInput,
    Texture* pTexDepthInput,
    SubTexture* pSubTexA,
    SubTexture* pSubTexB,
    Texture* pTextureOutput);

FUNCTION_NAMED_ARGS(SomeFunc,
    obj,
    randomData,
    someCamera,
    configData,
    dynamicIntensity,
    someInfo,
    shader,
    pTexInput,
    pTexDepthInput,
    pSubTexA,
    pSubTexB,
    pTextureOutput);

// .cpp
SomeFunc(
    SomeFunc_Arg::obj              = obj,
    SomeFunc_Arg::randomData       = randomData,
    SomeFunc_Arg::someCamera       = someCamera,
    SomeFunc_Arg::configData       = data,
    SomeFunc_Arg::dynamicIntensity = dynamicIntensity,
    SomeFunc_Arg::someInfo         = someInfo,
    SomeFunc_Arg::shader           = *pSomeShader,
    SomeFunc_Arg::pTexInput        = pSomeTexInput,
    SomeFunc_Arg::pTexDepthInput   = pTexDepth,
    SomeFunc_Arg::pSubTexA         = pSomeSubTexA,
    SomeFunc_Arg::pSubTexB         = pSomeSubTexB,
    SomeFunc_Arg::pTextureOutput   = pSomeSurface);

Using a separate function that accept operator=  constructors, automatically created

  • All parameters are required.

  • Type safe.

  • The syntax can be weird, but even though you are using a lot, the function implementation is completely untouched.
