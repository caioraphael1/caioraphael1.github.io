Value: Keywords

🕒 Created: 2023-10-11 | Updated: 2026-11-24

constexpr  (C23) / (C++11) 

int a = 10;
constexpr int b = a; // ERROR: 'a' is not a constant expression

constexpr int a = 10;
int b = a + 5;  // OK

constexpr int a = 10;
a = 20;  // ERROR: cannot modify a constexpr object

constexpr  for pointer (C++11)

  • "The value must be known and validated at compile time."

  • I call this "comptime const". 

constexpr int* b = nullptr; // Valid

int a = 10;
constexpr int* b = &a; // ERROR: 'a' does not have static storage duration

  • A C++ constexpr  pointer is itself constant. It is effectively a T* const , not a const T* .

  • C does raises an error in both cases.

const  (C89) / (C++98)

  • "The object cannot be modified through that identifier."

  • This does not  mean comptime constant; see constexpr  for that.

  • I call this "user const guarantee".

Read and Write 

int a = 10;
const int b = a; // OK

const int a = 10;
int b = a + 5;  // OK

const int a = 10;
a = 20; // ERROR: cannot modify a const object

Syntax permutations and pointers

  • Interpretation rules:

    1. Read the declaration right to left.

    2. const  applies to whatever is immediately to its left. If nothing is to its left, it applies to the thing immediately to its right.

    3. There's no such thing as (const*) , for example: T const*  should be interpreted as (T const)* , and not T (const*)

| Declaration            | Can change a  | Interpretation                                                                |
|------------------------|:--------------:|-------------------------------------------------------------------------------|
| const T a = b;        |       No       | const(T)                                                                     |
| T const a = b;        |       No       | const(T)                                                                     |
| const T const a = b;  |       -        | (C: Valid, but redundant) / (C++: Invalid via duplicate qualification of T ) |
| const const T a = b;  |       -        | (C: Valid, but redundant) / (C++: Invalid via duplicate qualification of T ) |
| T const const a = b;  |       -        | (C: Valid, but redundant) / (C++: Invalid via duplicate qualification of T ) |

| Declaration             | Can change a  | Can change *a  | Interpretation                                      |
|-------------------------|:--------------:|:---------------:|-----------------------------------------------------|
| const T* a;            |      Yes       |       No        | const(T)*  / "Pointer to const T "                |
| T const* a;            |      Yes       |       No        | const(T)*  / "Pointer to const T "                |
| T* const a = b;        |       No       |       Yes       | const(T*)  / " const  pointer to T "              |
| const T* const a = b;  |       No       |       No        | const(const(T)*)  / " const  pointer to const T " |
| const T const* a = b;  |       -        |        -        | Invalid via duplicate qualification of T           |
| const const T* a = b;  |       -        |        -        | Invalid via duplicate qualification of T           |
| T* const const a = b;  |       -        |        -        | Invalid via duplicate qualification of pointer      |
| T const* const a = b;  |       No       |       No        | const(const(T)*)  / " const  pointer to const T " |
| T const const* a = b;  |       -        |        -        | Invalid: duplicate qualification of T              |

  • If you can't change a , then the value must be initialized at declaration.

Propagation / Recessiveness

  • const  on an object is “shallow but recursive through members”.

  • It makes every direct and nested member const , so it can't be written to.

  • BUT, if the member is a pointer , there can still be mutability!

    • The member int* pB  in a const  struct, becomes int* const pB , meaning you can't change pB , but you can change *pB !!

    • To avoid that, the pointer inside the struct should be it self protected, regardless if the struct is const  or not, via const int* pB , so when if the struct is created as const , the pointer becomes const int* const pB .

      • const int* pB : You can change pB , but you can't change *pB .

      • const int* const pB" : You can't change pB  and you can't change *pB .

    • Even if this wasn't the case, this would still break if you create a copy of this const  object, so suddenly you can modify *pB  anyway.

    • It's simply not what C++ does. It doesn't handle well deep const  propagation and copy const  edge cases.

    • This is not the case for all languages. Check the section below. 

struct MyStruct2
{
    int c;
    int* pD;
};

struct MyStruct1
{
    int a;
    int* pB;
    MyStruct2 ms2;
};

int tmp = 10;
MyStruct1 ms_temp = {};


const MyStruct1 ms1 = {};

ms1         = ms_temp; // INVALID: whole object is `const`, can't be assigned.

ms1.a       = 1;       // INVALID: `a` is `const int`.
ms1.pB      = &tmp;    // INVALID: `pB` is `int* const`, the pointer itself can't change.
*ms1.pB     = 2;       // OK: pointee is plain `int`, not `const`.

ms1.ms2.c   = 3;       // INVALID: constness propagates into nested structs
ms1.ms2.pD  = &tmp;    // INVALID: `pD` is `int* const`
*ms1.ms2.pD = 4;       // OK: pointee is plain `int`


const MyStruct1* const pMs1 = &ms1;

pMs1          = &ms_temp; // INVALID: pointer is `const`
*pMs1         = ms_temp;  // INVALID: pointee is `const`

pMs1->a       = 2;        // INVALID: `(*pMs1).a` is `const int`
pMs1->pB      = &tmp;     // INVALID: `(*pMs1).pB` is `int* const`
*pMs1->pB     = 3;        // OK: pointee of `pB` is plain `int`

pMs1->ms2.c   = 2;       // INVALID: `(*pMs1).ms2` is `const MyStruct2`, so `c` is `const int`
pMs1->ms2.pD  = &tmp;    // INVALID: `pD` is `int* const`
*pMs1->ms2.pD = 3;       // OK: pointee of `pD` is plain `int`
In other languages

  • Rust:

    • There is &T  (shared, read-only) and &mut T  (exclusive, writable), and it propagates through references automatically. 

    struct S<'a> {
    a: i32,
    b: &'a mut i32,
    c: Box<i32>,
}

fn f(s: &S) {
    s.a = 1;      // ERROR
    *s.b = 2;     // ERROR: can't mutate through a & reference, even though b is &mut
    *s.c = 3;     // ERROR: Box owns its contents, so immutability flows through
}

    • Having a &S  means you can only get & access to everything reachable through references and owning types (Box, Vec, String). This is a “deep const”, and it’s the default.

    • Raw pointers ( *const T , *mut T ) don't propagate, just like C. You need unsafe to dereference them.

    • Interior mutability ( Cell , RefCell , Mutex , Atomic* ) lets a type opt into mutation through & .

    • Shared ownership ( Rc<T> , Arc<T> ) only gives you &T anyway.

    • For copies, Rust avoids the problem because &T  isn’t convertible to &mut T , and owning types require explicit .clone()

  • D:

    • It propagates through nodes, just like Rust does.

    • It also handles copy differently, by making that copy an error for types containing mutable indirections, which means const S becomes a different kind of thing from S.

  • Zig:

    • Same as C. It puts constness in the pointer type ( *T  vs *const T , []T  vs []const T ), and it does not propagate through a pointer field.

Promotion to comptime constant

  • For const T a = b; , if b  is a comptime constant, how should we interpret a ?

  • In C:

    • It doesn't promote to a "comptime constant", so a  cannot be used for int array[a]; , for example.

  • In C++:

    • It promotes to a "comptime constant", so a  can be used for int array[a]; , for example.

static  (C89) / (C++98)

For Global variables

  • Gives Internal linkage (private to the translation unit). 

    // file_a.cpp

static int counter = 0;

static void InternalFunction()
{
}

    • Neither counter  nor InternalFunction  can be referred to by name from another translation unit.

  • And also give static storage (lives through the whole app).

For Local variables

  • Static storage duration

For Class Data Members (C++98)

  • One variable shared by all instances.

inline  variables (C++17)

Header defined variables

  • This allows the variable to be defined in a header included by multiple translation units without creating multiple-definition errors.

  • C doesn't have this usage.

Without inline 
// constants.h
constexpr float PI = 3.1415926535f;

// main.cpp
#include "constants.h"  // Will have a definition of `PI` in its TU.

// other.cpp
#include "constants.h"  // Will have another definition of `PI` in its TU; which will then give linkage errors, as it violates the 'One Definition Rule (ODR)'.
With inline 
// constants.h
inline constexpr float PI = 3.1415926535f;

// main.cpp
#include "constants.h"  // Will have a definition of `PI` in its TU.

// other.cpp
#include "constants.h"  // Will have another definition of `PI` in its TU; but as the variable is inlined, it will not give linkage errors.

restrict  (C99) 

void add(float *restrict dst,
         const float *restrict a,
         const float *restrict b,
         int count)
{
    for (int i = 0; i < count; ++i) {
        dst[i] = a[i] + b[i];
    }
}

  • The compiler can assume that the objects modified through dst are not also accessed through a or b in a conflicting way during the execution of this function.

  • It's an aliasing optimization. All the above means: "do not alias".

  • Without restrict , compiler must conservatively assume aliasing.

  • Very significant in hot loops:

    • enables vectorization

    • enables load/store reordering

    • reduces reloads from memory

    • improves auto-SIMD generation

  • Incorrect use causes undefined behavior and real miscompilations.

  • Can be used in function parameters, or for any other variable.

  • C++ doesn't have it, but you can:

    • GCC

      • __restrict__ , __restrict

    • Clang

      • __restrict__ , __restrict

    • MSVC

      • __restrict

    • Intel compilers

      • __restrict  and compiler-specific alternatives

volatile  (C90) / (C++98)

  • It tells the compiler that accesses to this object have special observable behavior and must respect volatile semantics. 

volatile int hardware_register;

  • Common applications:

    • Memory-mapped hardware registers.

    • Certain hardware interfaces.

    • Low-level embedded programming.

  • It does NOT provide:

    • Atomicity.

    • Thread synchronization.

    • Memory ordering guarantees between threads.

  • For multithreaded code, use std::atomic  instead.

_Thread_local  / thread_local  (C11) / (C++11)

  • Each thread receives its own instance.

  • You can combine it with static  or extern : 

static thread_local int counter = 0;
extern thread_local int counter;

_Atomic  (C11)

  • Atomic type qualifier.

  • Provides atomic operations on the object. 

#include <stdatomic.h>

_Atomic int counter;

_Atomic(int) counter;

  • Unlike volatile , atomic operations provide concurrency semantics.

[[maybe_unused]]  (C23) (C++17)

  • Suppresses unused warnings explicitly, documenting intent. 

[[maybe_unused]] int debug_flag;

[[no_unique_address]]  (C++20)

  • For :

    • Struct members.

    • Class members.

  • Allows a non-static data member (typically empty type) to occupy no storage. 

struct Empty {};
struct S {
    int x;
    [[no_unique_address]] Empty e;
};

  • Without it:

    • e  may consume 1 byte

  • With it:

    • e  can overlap with padding

    • object size may shrink

  • Optimization impact

    • reduces object size

    • improves cache density

    • improves container packing

extern  (C89) / (C++98)

  • Jacob Sorber - Extern Keyword

  • It makes a declaration, without allocating storage; it tells that the definition will come from elsewhere.

  • A declaration tells the compiler something exists. 

int foo;

  • Surprisingly, in C, this is actually both a declaration and a definition. It allocates storage. 

.data
foo:
    4 bytes

  • Now consider: 

extern int foo;

  • This is only a declaration.

  • "Somewhere, there is an int foo. Trust me."

  • No storage is allocated.

constinit  (C++20)

  • The data requires static initialization, but allows subsequent modification.

  • Its main purpose is preventing accidental dynamic initialization of global and thread-local variables. 

constinit int global_value = 42;

int main()
{
    global_value = 100; // OK
}

  • The variable is initialized during static initialization, but it remains mutable.

mutable  (C++98)

  • Allows modification even through a const object.

  • Seems extremely stupid, creating some hidden exceptions to what was supposed to be a const behavior. 

class MyClass
{
    int value = 0;
    mutable int cache = 0;

    void Update() const
    {
        // value = 10; // ERROR
        cache = 10;    // OK
    }
};

register  (C90) / (C++98)

  • It was intended to give the compiler a hint that a variable would be accessed frequently and should preferably be stored in a CPU register.

  • Historically, CPU registers were significantly faster to access than main memory.

  • However, modern compilers perform register allocation automatically.

  • It is largely obsolete today.

  • C++11:

    • Deprecated.

  • C++17:

    • Removed.

  • C98 -> C23:

    • Supported. 

void Calculate(void)
{
    register int counter = 0;

    for (counter = 0; counter < 1000; ++counter)
    {
        // ...
    }
}
