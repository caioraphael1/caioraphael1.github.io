Keywords for Functions / Methods

🕒 Created: 2023-10-11 | Updated: 2026-11-15

const  (C89) / (C++98)

For Class Methods (C++)

  • The const  at the end means that this  will be const MyClass* this; , which means you can't write to any class data members .

    • The reason for that is how internally member access is made through this->mMyMember , and with the const  applied above, that means that you can't write to *this . 

class MyClass
{
    mMyMember int = 0;

    void DoSomething() const;
}

void MyClass::DoSomething() const
{
    int b = mMyMember; // OK

    mMyMember = 2; // ERROR
}

constexpr  (C++11)

  • "The value must be known and validated at compile time."

  • I call this "comptime const".

  • A constexpr  function is not necessarily executed at compile time. It is eligible for compile-time evaluation when its arguments and context permit it. 

constexpr int square(int x)
{
    return x * x;
}

constexpr int a = square(10);

  • The compiler must be able to evaluate square(10)  during compilation when used to initialize result.

  • But the function can also be called at runtime: 

int a = 5;
int b = square(a);

  • Further changes:

    • C++14

      • Relaxed the restrictions on constexpr  function bodies, allowing local variables, loops, and more complex control flow.

    • C++17

      • constexpr  lambdas and additional library support.

    • C++20

      • constexpr  virtual functions, dynamic allocation in constant evaluation, more library support.

    • C++23

      • Further relaxation, including constexpr  functions that can use non-literal variables in certain circumstances.

consteval  (C++20)

  • It's basically a strong version of constexpr  for functions; it does not allow ordinary runtime execution 

consteval int square(int x)
{
    return x * x;
}

int main()
{
    constexpr int a = square(10); // OK: 100

    int b = 10;
    // int c = square(b);         // ERROR
}

  • A function cannot simultaneously be declared constexpr  and consteval .

  • consteval  cannot be applied to destructors, allocation functions, or deallocation functions.

inline  (C99, C++98)

1) It gives the illusion of inlining a function

  • It tells the compiler "Prefer to inline the function (copy/paste it to where it's used), but that's just a suggestion, you can do what ever you want, I don't want to be a bother".

  • As the compiler usually choses to ignore the programmer, using inline  like this does basically nothing.

  • Using inline  like this is just a futile attempt for control.

Performance

  • inline  rarely changes performance today.

  • Calling a function generally causes a certain overhead (stacking arguments, jumps, etc...), and thus for very short functions, it may be more efficient to simply insert the code of the function where it is called, instead of performing the process of formally calling a function.

  • Preceding a function declaration with the inline  specifier informs the compiler that inline  expansion is preferred  over the usual function call mechanism for a specific function. This does not change at all the behavior of a function, but is merely used to suggest  the compiler that the code generated by the function body shall be inserted at each point the function is called, instead of being invoked with a regular function call.

  • Most compilers already optimize code to generate inline functions when they see an opportunity to improve efficiency, even if not explicitly marked with the inline specifier. Therefore, this specifier merely indicates the compiler that inline is preferred for this function, although the compiler is free to not inline it, and optimize otherwise. In C++, optimization is a task delegated to the compiler, which is free to generate any code for as long as the resulting behavior is the one specified by the code.

  • Modern compilers ignore it as an inlining hint if they choose.

2) Header defined functions

Without inline 
// math.h
#pragma once  // <- Prevents the header from being included more than once within the same TU.

int add(int a, int b) {
    return a + b;
}

// main.cpp
#include "math.h"  // Will have a definition of `int add(int a, int b)` in its TU.

// other.cpp
#include "math.h"  // Will have another definition of `int add(int a, int b)` in its TU; which will then give linkage errors, as it violates the 'One Definition Rule (ODR)'.
With inline 
// math.h
#pragma once  // <- Prevents the header from being included more than once within the same TU.

inline int add(int a, int b) {  // <- Permits multiple equivalent definitions across TUs.
    return a + b;
}

// main.cpp
#include "math.h"  // Will have a definition of `int add(int a, int b)` in its TU.

// other.cpp
#include "math.h"  // Will have another definition of `int add(int a, int b)` in its TU; but as the function is inline, it will not give linkage errors.
For class functions (C++)

  • Methods (class functions) are implicitly inline. 

struct Vector2 {
    float x, y;

    float length_squared() const {
        return x * x + y * y;
    }
};

  • same as: 

struct Vector2 {
    float x, y;

    inline float length_squared() const {
        return x * x + y * y;
    }
};

Alternatives

  • GCC / Clang:

    • __attribute__((always_inline))

  • MSVC:

    • __forceinline

  • Those are stronger hints ( still not absolute guarantees ).

[[nodiscard]]  (C23) / (C++17)

  • Is an attribute that tells the compiler to warn if the return value of a function (or certain types) is ignored. 

[[nodiscard]] int compute();

void f() {
    compute(); // warning: return value discarded
}

  • Applicable to:

    • functions

    • constructors

    • class/struct/enum types

  • In C:

    • Not available in older C standards (C11, C17, etc.)

    • Standardized in: C23

  • In C++:

    • Standardized in: C++17 

      [[nodiscard]] int parse();

    • Enhanced in: C++20 (added message support) 

      [[nodiscard("check the error code")]]
int parse();

  • Old alternatives

    • GCC / Clang 

      __attribute__((warn_unused_result))
int compute(void);

    • MSVC 

      _Check_return_
int compute(void);

[[reproducible]]  (C23) 

[[reproducible]]
int pure_compute(int x);

  • Guarantees that the function:

    • has no observable side effects

    • depends only on its arguments and possibly global state

    • produces consistent results

  • The compiler may transform: 

    int a = f(10);
int b = f(10);

  • into: 

    int a = f(10);
int b = a;

  • Optimization impact

    • Allows:

      • common subexpression elimination

      • redundant call elimination

      • hoisting out of loops

      • reordering relative to unrelated side effects

  • Vendor equivalents in both languages:

    • __attribute__((pure))

[[unsequenced]]  (C23)

  • Stronger than [[reproducible]] .

  • Indicates:

    • no side effects

    • no synchronization

    • no inter-thread interaction

    • can be evaluated in unsequenced context 

[[unsequenced]]
int fast_math(int x);

  • Optimization impact

    • Allows:

      • aggressive reordering

      • call merging

      • vectorization

      • evaluation in arbitrary order

      • removal if result unused

  • Vendor equivalents in both languages:

    • __attribute__((const))

static  (C89) / (C++98)

For Global Functions

  • In C :

    • Makes the function private to the Translation Unit.

  • In C++ :

    • Makes the function private to the Translation Unit.

      • It's preferred to use Anonymous Namespaces for the same result.

  • It's the traditional way to give a function internal linkage.

  • The linker does not export its symbol.

  • Other translation units cannot call it, even if they declare it with extern .

  • If a function is only used inside tht TU, making it static expresses that intent.

  • Because the compiler knows nobody outside the Translation Unit can call the function, it can sometimes:

    • inline it more aggressively

    • remove it entirely if unused

    • specialize it

    • rename or merge it freely.

For Class Methods (C++)

  • No this  pointer; callable without an object.

  • The function now belong to the class, not to the instance.

_Noreturn  (C11), [[noreturn]]  (C++11)

  • Indicates a function never returns. 

[[noreturn]] 
void fatal();

  • It's a guarantee, not just documentation. They can affect code generation.

  • They state that a function:

    • never returns normally

    • either calls exit, abort, longjmp, or loops forever

    • reaching the end is undefined behavior

  • The compiler:

    • does not require a return

    • removes code after the call

    • may remove stack cleanup logic

[[deprecated]]  (C23, C++14)

  • Marks APIs as obsolete. 

[[deprecated("Use new_api instead")]]
void old_api();

extern  (C89) / (C++98)

  • extern  makes a declaration, without allocating storage; it tells that the definition will come from elsewhere.

  • Functions already default to external  linkage: 

void hello(void);

  • means 

extern void hello(void);

  • So this is not something you have to worry about.
