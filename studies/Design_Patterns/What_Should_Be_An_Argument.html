What Should Be An Argument

🕒 Created: 2026-11-12 | Updated: 2026-11-12

Let's discuss some examples

  • Consider a struct Car  containing an internal position , direction  and speed .

    • Should we do:

      1. Drive(&car) ? 

        void Drive(pCar)
{
    pCar->pPosition += pCar->direction * pCar->speed; 
}

      2. or Move(&car.position, car.direction, car.speed) ? 

        void Move(pPosition, direction, speed)
{
    *pPosition += direction * speed; 
}

    • That's a very interesting question, that is answered by compression.

    • The first one is a compressed version of the second, but loses data flexibility. The first function can only move a Car , while the second function can move anything, as long as you have some form of definition of a position , direction  and speed .

    • What should you choose? There's not usually a right answer, but you should first opt for Move(&car.position, car.direction, car.speed) , as it gives you the best data transformation flexibility, and only move to Drive(&car)  if this gives you a concrete benefit in your API design. Don't force the design into Drive(&car)  at first, as you might be probably constraining yourself for no reason.

  • Consider a struct Car  containing an internal position , direction , speed , color , model , name .

    • Should we do:

      1. Drive(&car) ?

      2. or Move(&car.position, car.direction, car.speed) ?

    • Differently of the first example, the first option is now moving double the data across the API; it should only need position , direction , speed , but you are sending color , model , name  as well. This weighs heavily in the decision between (1) and (2).

    • From an API perspective:

      • You are not being explicit about the data you are going to interact with. You are passing way more that than the data than needed. You could be sending a whole universe of data through the Car  struct. This breaks any control over the changes inside the function. A exaggerated example would be passing a pointer to a global variable. It doesn't help you distinguish which data is relevant for this function.

      • A mathematical example is calling f(x, y, z, w, f, g, a, b, c, d, e, f, g, ...) , but the output of this function only depends on x  and y . This doesn't make sense! The transformation is a mathematical function of x and y , so it should just be f(x, y) .

    • From a performance perspective:

      • The problem isn't the cost of passing the arguments, as for Drive(&car) , the argument is only a pointer (4/8 bytes).

      • The performance issue is actually hidden inside Car : when we examine the machine operations, the cold data ( color , model , name ) gets pulled into the cache lines alongside hot data ( position , direction , speed ); Array of Structures vs Structure of Arrays. This is especially visible when you call Drive  lots of times, giving a much worse cache locality, with much more cache misses, bottlenecking performance.

      • Decoupling the signature to Move(&car.position, car.direction, car.speed)  frees you from Car , allowing you to pack hot data contiguously in memory and achieve way way better performance.

      • Avoiding this is the principal design of ECS and Data Normalization techniques, as applied to Relational Databases.

    • The option (1) is fundamentally what OOP is doing under the hood, for every single function call .

  • Consider a class Car  containing an internal position , direction , speed , color , model , name .

    • Should we do:

      1. car.Drive() ?

      2. There's no other options, as demonstrated.

    • All parameters that Drive  requires are defined as methods inside the Car  class, which are accessed by the implicit self / this  argument in the call.

    • From an API perspective:

      • You lose control over what is being changed inside the function, following the same arguments as for Drive(&car) . But, as we have the data  and behavior  coupled through the Car::Drive  method and the Car  member variables, this whole problem gets even worse. When start having to consider different accessor modifiers and inheritance behaviors.

      • Simply said, everything is an object, and there's no longer any trivial data transformations. This is the least flexible design by far. 

      Drive();
void Car::Drive()
{
    // You assume it's just changing the `position` by the `direction` and `speed`, 
    // but it could technically be changing the car's `color`, `model` and `name`. 
    // You have no guarantees about the data transformation.
    // You sent everything to the function, and there's no contract that tells the 
    // function what it should and shouldn't touch. 
    // Good luck.
}

    • From a performance perspective:

      • It's the exact same argument as Drive(&car) , you end up having much worse performance due to worse cache locality.

      • It actually gets even worse when you consider the extra indirection methods give, as an OOP language now has to keep track of the data and behavior relationship. It has to use VTables (table of function pointers) to keep track of virtual functions / interfaces.

      • It gets even worse when we talk about memory!

        • Class instances are encouraged to be heap-allocated, which depending on your allocation method (usually via a general-purposed allocator ( malloc  / new ), default in C++), you will inevitably get heap fragmentation and have even worse performance with execution time of the application. You now not only have worse cache locality, but you are guaranteed to be pointer chasing on a fragmented heap.

        • We could go even further and talk about the design implications of having a object-oriented language, such as "smart pointers", "shared pointers", "unique pointers", "garbage collection" and "RAII". All of this hurts performance, and it comes from a very clear design philosophy of trying to replace the core idea of data and memory by a high-level human abstractions of that data. I won't go further into memory here, but I hope I'm getting my point across about OOP's performance.

    • As demonstrated in the previous examples, this design, therefore:

      1. Goes against many of FP principles, that would lead to much more readable, safe and predictable code.

      2. Drives you towards much less flexible designs, via a way-too-early compression, as it tries to encapsulate things into objects as soon as possible.

      3. Completely disregards cache locality, by pure definition of how it handles its methods via self / this , while also encouraging "smart" (and slow) memory designs. Memory is just a large array of data, it's simple, but as soon as you try to abstract what the data actually is, molding it into something only a human could understand, the machine struggles, and the design struggles. OOP languages go for some desperate attempts to deny how memory works by being "smart". A harder and impractical design, now requires "smart solutions".

What is a good design?

  • For API flexibility:

    1. Don't compress data too early. You might be constraining the API too early.

      • We should aim to group data based on how it's used, grouping hot data that always travels together. We shouldn't group data by how it makes you feel from an arbitrary human perspective.

      • One of the consequences of this is: don't use classes. Classes are fundamentally about compressing data and behavior into an object, even when you don't need to.

  • For API maintainability and safety:

    1. Avoid global variables as much as possible.

      • Everything the function needs should be passed by function arguments.

      • (See the Drive(&car)  vs Move(&car.position, car.direction, car.speed)  example).

      • This can lead to some API designs dilemmas, where you could have a slightly better ergonomics if the user isn't required to pass around states it doesn't care about. Though, this decision should be taken carefully and should usually be one of the last step on the API design.

    2. Avoid passing more data than what the function needs.

      • Sometimes, compressing data looks good for the API, but doing it too early is a terrible decision.

      • One of the consequences of this is: don't use classes. Classes are fundamentally about compressing data and behavior into an object, even when you don't need to. Any method call will send a whole pointer to the class instance implicitly ( self / this ), which almost always means that you are passing way more data than what the function requires.

    • This keeps the function as being just a local data transformation, and nothing else. No hidden behavior. Keep the data tight, and the transformation deterministic.

  • For performance:

    1. Avoid passing more data than what the function needs, that hurts cache locality.

      • Sometimes, compressing data looks good for the API, but doing it too early is a terrible decision.

      • One of the consequences of this is: don't use classes. Classes are fundamentally about compressing data and behavior into an object, even when you don't need to. Any method call will send a whole pointer to the class instance implicitly ( self / this ), which almost always means that you are passing way more data than what the function requires.

      • (See the Drive(&car)  with extra data vs Move(&car.position, car.direction, car.speed) , or car.Drive() , for examples)

As a philosophy

Presenting: Data Oriented Design

  • Separate the data  and data transformations ; don't treat data  and behavior  as the same thing.

  • It tells you that you should think of data as just being data, instead of a high-level human abstraction of an object.

  • This lets you work side by side of how the CPU/GPU was meant to work, giving you a much better performance, while unlocking more flexibility for deconstructing unnecessary constraints we placed ourselves by using OOP.

  • This design philosophy is also extremely useful for highly parallel tasks, making multi-threading much much easier. One of the examples of this is ECS and Bindless Resources on the GPU.

  • This doesn't tell you how to do the transformations or how to handle scopes, for that you should use Functional Programming (see below).

Presenting: Functional Programming

  • It tells how  the data transformation  should happen. If you are using DOD, that means "how to define your functions".

  • It cares about data purity, locality, mathematical determinism.

  • One of the most important characteristics is not using globals.

    • If the function has everything it needs via its params:

      • The function has no agency over the system, it's just a transformation.

      • It has "limited permissions"; it can only act within things inside its scope.

    • If the function doesn't have params and relies on getting data from the global space:

      • The function has complete agency over everything. It can modify things that it shouldn't.

      • It has "elevated permissions".

      • It can be slightly more efficient, but it gets chaos in return.

  • This lets you have a much safer code, with no hidden behavior, predictable code, and strong focus on explicit transformations. A code that follows that should be much easier to read, to maintain, and to optimize.

  • It doesn't tell you how you should handle the relationship between data  and data transformations , for that you should use Data Oriented Design (see above).
